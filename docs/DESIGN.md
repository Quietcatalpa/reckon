# 设计说明

README 讲怎么用，这里讲它是怎么判断的、为什么这样设计。

## 清理：怎么判断

| 对象 | 判断方式 |
|---|---|
| 缓存目录（临时文件、浏览器/应用缓存、pip/npm、HuggingFace 模型、node_modules、`__pycache__`） | 纯规则，整块作为一项 |
| 重复文件 | 按大小 → 首尾 64KB → 完整哈希；保留整理过的那份，其余建议删除。>256MB 的只抽样 16 块，抽样一致只算「疑似重复」（需要你看） |
| 安装包、图片、视频、音频 | 只按放了多久判断，不送模型；媒体文件最多到「需要你看」 |
| 文档、代码、数据、日志、压缩包、其他 | 规则先验 × 0.45 + Laya × 0.55；能读的文件会读开头约 600 字给模型参考 |

**规则先验**由位置（临时目录 / 下载 / 应用数据 / 个人目录 / 聊天软件接收目录）、类型、多久没修改、
文件名像不像副本、旁边有没有解压出来的同名文件夹等决定，见 `decide.rule_prior`。

- **备份文件**（.bak / .old / .backup / .bk / .orig）单独一类：可能是唯一的一份，一律封顶在「需要你看」。
- **压缩包旁的同名文件夹**只是线索。zip 会核对文件列表和大小，确认全部都已解压（兼容多套一层同名文件夹的解压方式、GBK 文件名）才提高到建议删除；
  rar/7z 读不了目录、或核对不上时只加一点分，并注明「只作参考」。

**Laya** 对每个文件回答一个二选一问题「删除 / 保留」（每个选项附一句说明），取「删除」的概率参与融合。
我们也试过是/否类（noul）问题，比如「删除这个文件是安全的」，但它对几乎所有文件都给出 0.9 以上，区分不开，所以没有用。
在 12 个真实文件上的**初步对比**：二选一答对 9 个，剩下 3 个在 50% 附近，按阈值会落进「需要你看」。样本太少，只能说明方向，不能当准确率。

**清理建议分**：规则先验和 Laya 加权得到的 0–100 分，用来排序和分栏，**不是**校准过的「删了没事」概率。
界面上每项同时写明依据：完整比对确认重复 / 疑似重复（抽样）/ 规则 + Laya（读过内容片段或只看文件信息）/ 只按规则。

**阈值**：建议分 ≥ 70 建议删除，40–70 需要你看，< 40 建议保留。以下情况封顶在「需要你看」：

- 桌面/文档/图片/视频目录里的文档、代码、数据；
- 微信/QQ/企业微信等聊天软件接收的文件（安装包和日志除外）。重复副本不受限制，因为另一份还在；
- 所有备份文件。

**主题标签**（课程学习 / 竞赛科研 / 求职升学 / 个人生活 / 软件工具）优先按路径和文件名关键词判断，
没有命中时才用 Laya 的分类（把握 ≥ 50%）。Laya 的主题分类实测不太准（PPT 常被分成「软件工具」），只作补充。

**模型判断的方式**（第二轮调整，数字都是在一台普通笔记本 CPU 上实测的）：

- **不设数量上限**，所有需要模型的文件都判断；页面上的「模型最多判断」留空就是全部，填了数字才限制。
- **先判断最需要的**：规则拿不准的（规则分 0.3–0.85）最先，其次是规则认为该删的（最需要模型把关），规则已经认为该留的放最后；
  同一档里大文件优先。所以中途点「停止」，已经判断的是最有价值的那部分。
- **记住结论**：`%LOCALAPPDATA%\Reckon\laya_cache.json` 按路径记下每个文件的判断，大小和修改时间都没变就直接沿用。
  问题文本、片段长度或模型版本一变，缓存整体作废。只保留本次扫描还存在的文件。
- **不再问主题**：每多问一个问题，Laya 就要把整段内容再算一遍。实测「删除/保留 + 主题」1489 ms/个，只问「删除/保留」791 ms/个；
  而 Laya 的主题分类本来就不准，所以主题只按关键词判断。
- **内容片段保持 600 字**：300 字只快约 20%（真实文件上 353 → 281 ms/个），60 个真实文件里 57 个结果一致，
  变了的 3 个全是压缩包：它的“内容”是文件列表，截短后丢了关键信息。
- **没有做批量推理**：实测在 CPU 上一次喂 4 个只快约 12%，喂 16 个反而更慢，不值得增加复杂度。
- 内容片段用 4 个线程提前读好，和模型判断同时进行。
- 没下完的下载（.part / .crdownload 等）和崩溃转储（.dmp）一定是垃圾，直接按规则判断，不送模型
  （模型对这类文件没有帮助，还会把分数往下拉）。日志仍交给模型，因为训练日志、实验记录可能有用。

**评估集**：`docs/eval/cases.jsonl` 是 68 条手工编写并标注的虚构样例（26 该删 / 20 该看 / 22 该留），
`python docs/eval/run_eval.py` 会用和扫描完全相同的代码比较不同设置。当前结果：

| 设置 | 标注一致 | 该留→被建议删除 | 该看→被建议删除 | 该删→被建议保留 |
|---|---|---|---|---|
| 只用规则 | 46/68 | 0 | 1 | 0 |
| 规则 0.30 + Laya 0.70 | 50/68 | 0 | 0 | 2 |
| **规则 0.45 + Laya 0.55（默认）** | **49/68** | **0** | **0** | **0** |
| 规则 0.60 + Laya 0.40 | 47/68 | 0 | 0 | 0 |

选 0.45：一致数只比 0.30 少 1，但没有「该删的被建议保留」。把「需要你看」的下限从 0.40 调低到 0.30/0.35 没有改善，保持不变。
剩下的不一致大多是「该看」被判成「建议保留」（都不会被删），标注本身也有主观性。
样例少、是编的，这些数字只用来比较设置、防止改规则时变差（测试里会检查只用规则时「该留→被建议删除」必须为 0），不能当准确率。

**能读内容的格式**：txt/md/log/csv/json/代码、docx、pptx、xlsx（100MB 以内）、pdf、zip（只看文件列表）、ipynb。
OneDrive 等云端占位文件不读取内容（读取会触发下载）。

## 整理：怎么找去处

交进来的是文件夹时只整理第一层：散落的文件逐个安排，子文件夹整体移动（不拆开），因为子文件夹通常是一个项目或解压出来的软件。

**按主题**：读取目标文件夹下最多 3 层的子文件夹，依次尝试：

1. **同名匹配**：文件名（或子文件夹里的文件名）里出现了某个已有文件夹的名字。名字越长、越深越优先，
   出现在自己名字里比只出现在子项里可信。「作业」「资料」「数据」等太笼统的名字不参与匹配，
   否则「数学作业」会被放进随便哪门课的「作业」文件夹。编号前缀（`01_`）会先去掉。
2. **关键词分组**：升学求职实习 / 竞赛 / 科研 / 英语 / 课程 / 学生事务 / 素材工具 / 个人生活。
   组名和目标文件夹的顶层分类名按两字词重叠对应，比如「个人生活」能对上「03_生活账单」。
3. **Laya**：在顶层分类里选一个（每个分类附带它下面几个子文件夹的名字作说明，另加一个「都不合适」），把握 ≥ 50% 才采用。
4. 都不行就标成「需要你选」。

**按类型**：分到 文档 / 代码 / 数据 / 安装包 / 压缩包 / 图片 / 视频 / 音频 / 临时与日志 / 其他。子文件夹保持不动。

**执行与撤销**：去处必须是方案里给出的选项之一（防止页面被篡改后移到任意位置）；重名时加 ` (2)`，不覆盖。

- 每次执行对应 `%LOCALAPPDATA%\Reckon\organize_history\` 里的一条记录。**每移动一项之前**先把「从哪移到哪」写进记录
  （先写临时文件再替换，断电也不会写坏），移动失败再把这条删掉。所以程序中途被关掉，已经移走的东西也都在记录里。
- 撤销时倒序处理每条记录：整理后的位置有、原位置没有 → 放回；原位置已经有了、整理后的位置没有 → 说明当时没来得及移动，
  直接算完成；两边都有或都没有 → 失败并说明原因。
- 放不回去的项留在记录里，处理好后可以点「再试一次」；**全部放回后**才标记为已撤销，并删除整理时新建、现在又空了的文件夹。

## 安全边界

- 不扫描、不整理：各盘的 `Windows`、`Program Files*`、`ProgramData`、`WpSystem`、回收站、系统卷信息等；
  软件目录（含卸载程序，或有 exe 加 3 个以上 dll，或是 Electron 应用）；conda 环境；`.git`；本工具自身目录；Laya 模型。
- 不整理：盘根目录、用户目录本身、AppData；隐藏/系统文件、`desktop.ini`、快捷方式。
- dll/pyd/asar 等程序组件不当作重复文件，也不会被建议删除；下载文件夹里解压出来的软件整个作为一项列出。
- **页面结果带编号**：每次扫描结果有 `scan_id`、每个整理方案有 `plan_id`，页面提交删除 / 整理时必须带上，
  对不上（比如在另一个页面重新扫描过）就拒绝，页面也会自动刷新成最新结果。删除、整理、撤销、扫描、生成方案互斥，同一时间只做一件事。
- **删除重复副本前**：确认保留的那份还在、修改时间和扫描时一样，再把两份逐块完整比对，不依赖扫描时的抽样结果。
- **有变化就不动的目录**：临时文件、下载里解压的软件、HuggingFace / .cache 模型缓存、node_modules、conda 包缓存，
  扫描时记下每个路径的最近修改时间，删除前重新统计，有新改动就跳过；浏览器 / 应用缓存本来就一直在变、随时能重建，不做这个检查。
- **整理软件目录**：交进来的文件夹本身或它的任意一层上级是软件目录（卸载程序、exe + 3 个以上 dll、Electron 应用、conda 环境），整个拒绝。
- **磁盘列表**：默认只勾本机硬盘；U 盘、网络盘标出来且不默认勾选（没有回收站，删除会被拒绝）；光驱不列，网络盘不查容量（断开时会卡住）。
- **内容解析**：docx/pptx/xlsx 超过 100MB、ipynb 超过 20MB、pdf 超过 300MB 不解析；单个文件解析超过 8 秒就放弃。
- 清理只移到回收站。Windows 在三种情况下会跳过回收站、直接永久删除：不是本机硬盘（U 盘、网络盘）；
  该盘回收站被设成「不将文件移到回收站」；单项比该盘回收站的容量上限还大。Send2Trash 在没装 pywin32 时
  会带着「不确认」参数调用系统接口，这几种情况会静默永久删除。所以删除前 `recycle.check` 会读取
  盘符类型和注册表 `BitBucket\Volume\{GUID}` 里的 `NukeOnDelete`、`MaxCapacity`，
  放不进去的一律拒绝（单项超过上限的 95% 也拒绝）。
- 删除前再次核对文件大小和修改时间，扫描后被改过的不删；删除重复副本前确认保留的那份仍然存在。
- 以上逻辑在 `tests/` 里都有测试（`python -m unittest discover -s tests -v`，GitHub 上每次提交自动跑），测试不会真的往回收站放东西。
- 服务只监听 127.0.0.1，校验 Host 头和每次启动随机生成的令牌，其他网页无法调用本地接口。

## 性能

以一台约 30 万个文件、C+D 两个盘的电脑为例：遍历约 30 秒，查找重复文件约 20–40 秒（4 线程并行，以前顺序计算约 1 分钟），
Laya 单独测约 0.35 秒/个，扫描时和读取内容、其他程序抢 CPU，实际约 0.7 秒/个。默认全部判断：
第一次约 850 个文件用了约 10 分钟，整次扫描约 12.5 分钟；第二次只有 5 个文件变了，整次扫描约 1.5 分钟。
以前限 300 个时，有 185 个非安装包文件没经过模型、只凭规则就被建议删除；现在只剩没下完的下载和崩溃转储这类（故意只按规则）。
模型加载 20 秒–1 分钟，在后台进行。

## 已知问题

- 在某些开发工具的后台进程里运行时，服务会在扫描途中被外部结束（进程直接退出、没有 Python 报错）。
  在独立的命令行窗口里运行（双击 `Reckon.exe` 或 `scripts\启动.bat`）没有这个问题。
- 只支持 Windows：路径规则、回收站、「发送到」菜单都是 Windows 的。

## 代码结构

```
reckon/            程序本体（python -m reckon）
  server.py        本地服务、任务调度、命令行入口（--demo / --organize / --install-sendto）
  scanner.py       遍历磁盘、识别缓存目录和软件目录
  dupes.py         重复文件（并行计算指纹、删除前完整比对）
  extract.py       读取文件内容片段（有大小上限和超时）
  decide.py        清理决策：规则先验、Laya 调用、融合、判断缓存
  laya_onnx.py     不依赖 torch 的 Laya 推理（onnxruntime + tokenizers）
  organize.py      整理：方案生成、移动、撤销
  rules.py         个人规则和阈值
  recycle.py       删除前检查能不能真的进回收站
  config.py        路径规则、类型表、数据目录
  sendto.py        「发送到」菜单
  web/index.html   界面（单文件，无构建步骤）
  demo/            演示模式的虚构数据
scripts/           启动/整理/发送到菜单的 .bat，导出 ONNX、打包 exe 的脚本
tests/             测试（GitHub 上每次提交自动跑）
docs/              设计说明、截图、演示数据生成（demo/）、评估集（eval/）
```

演示模式（`--demo`）下，清理和整理只在内存里模拟：界面照常变化，磁盘上不做任何读写。

**数据目录**：扫描结果、判断缓存、整理记录、个人规则存在 `%LOCALAPPDATA%\Reckon`（可以用环境变量 `RECKON_DATA` 改），
不在程序目录里，所以放在 Program Files 之类没有写权限的地方也能用。旧版本放在程序目录 `results/` 里的数据，第一次运行新版本时会自动搬过去。

**模型**：优先找 ONNX 版（`RECKON_MODEL_DIR`、exe 旁边的 `model/`、数据目录里的 `model/`、源码的 `build/laya-onnx/`），
找不到再用装好的 `laya` + torch 读 Hugging Face 缓存里的原版。ONNX 版由 `scripts/export_onnx.py` 导出：
decision head 里的注意力层手写了一遍（`nn.MultiheadAttention` 导出时会把序列长度写死），和原版的差 < 1e-6；
发布包用的是权重矩阵按半精度存储的版本（644 MB，加载时换回单精度计算），在 107 个样例上和原版的概率差 < 0.0001、分栏全部一致。
int8 量化试过：约 20% 的文件会换栏，没有采用。
